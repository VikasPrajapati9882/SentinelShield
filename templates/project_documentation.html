1. Project Overview

SentinelShield is a web-based Security Operations Center (SOC) dashboard designed to monitor, detect, record, and visualize suspicious activities and common web application attacks.

The project is built using Python Flask as the backend, HTML/CSS/JavaScript for the web interface, and MySQL for persistent storage of security alerts.

The main purpose of SentinelShield is to demonstrate how a basic SOC monitoring system can collect security events, analyze suspicious input, store alerts, and present them to a security analyst through a centralized dashboard.

2. Why I Created SentinelShield

In a real organization, applications continuously generate login attempts, requests, errors, and security-related events. Security analysts need a centralized system to identify suspicious activity and investigate possible attacks.

User Request ↓ Flask Application ↓ Security Detection ↓ Alert Generation ↓ MySQL Database ↓ SOC Dashboard ↓ Security Analyst Investigation

The project demonstrates basic SOC concepts such as alert generation, severity classification, source IP logging, threat detection, incident monitoring, and security event visualization.

3. Main Features

Login Monitoring Records login attempts, username, source IP, timestamp, and event information.
Attack Detection Detects indicators of SQL Injection, XSS, Path Traversal, and Brute Force Login Attempts.
Severity Classification Events can be classified as LOW, MEDIUM, HIGH, or CRITICAL.
MySQL Database Stores security alerts persistently.
SOC Dashboard Displays alerts, severity, IP addresses, timestamps, system status, and security metrics.
Threat Intelligence Can integrate with VirusTotal and AbuseIPDB for suspicious IP investigation.
Real-Time / Periodic Monitoring Allows newly recorded security events to appear on the dashboard.
Role-Based Access Supports roles such as Admin and SOC Analyst.

6. How SentinelShield Works

Step 1 - User opens the login page

The user visits the SentinelShield login page and enters a username and password.

Step 2 - Flask receives the request

The Flask application receives the POST request from the login form.

Step 3 - Source IP is identified

The application obtains the client's source IP. When a reverse proxy such as ngrok is used, forwarded headers can be used to identify the original client IP.

Step 4 - Input is analyzed

User-controlled input is passed through security detection functions.

  • SQL injection detector
  • XSS detector
  • Path traversal detector
  • Other attack detectors

Step 5 - Brute-force activity is checked

Failed authentication attempts can be counted by source IP. If the number of failed attempts reaches the configured threshold, the event can be classified as a possible brute-force attack.

Step 6 - Alert is generated

An alert can contain:

  • Event
  • IP address
  • Username
  • Severity
  • Timestamp
  • Threat status
  • Threat score
  • Incident status

Step 7 - Alert is stored

The alert is inserted into the MySQL alerts table.

Step 8 - SOC analyst views the alert

The dashboard reads alert information from MySQL and displays it in a centralized interface.

7. How to Run the Project

Step 1 - Install Python

python --version

Step 2 - Open the project folder

Open the SentinelShield project in Visual Studio Code or a terminal.

Step 3 - Create and activate a virtual environment

python -m venv venv

# Windows
venv\Scripts\activate

Step 4 - Install dependencies

pip install -r requirements.txt

If requirements.txt is not available:

pip install flask flask-socketio mysql-connector-python

Step 5 - Configure MySQL

CREATE DATABASE sentinelshield;

Create or import the required tables from the SQL file included with the project. Update the database connection settings with the correct host, username, password, database name, and port.

Step 6 - Configure Threat Intelligence APIs

If enabled, configure the required VirusTotal or AbuseIPDB API keys. Never publish API keys in GitHub or project documentation.

Step 7 - Start Flask

python app.py

Step 8 - Open the application

Open the local URL displayed by Flask, commonly http://127.0.0.1:5000.

8. How to Use the Dashboard

  1. Open the SentinelShield login page.
  2. Enter the required login information.
  3. Submit the form.
  4. Flask processes the request.
  5. Security detection logic analyzes the input.
  6. The event is stored in MySQL.
  7. The user is redirected to the dashboard.
  8. The SOC analyst reviews the recorded event.

9. Testing the Security Detection

Detection functions should be tested only against your own application or an authorized lab environment.

  1. Perform a controlled test using harmless test strings that match the detection rules.
  2. Open the SentinelShield dashboard.
  3. Check Recent Security Alerts.
  4. Verify the event name.
  5. Verify the source IP.
  6. Verify severity and timestamp.
  7. Verify the corresponding record in MySQL.
Security note: Do not use SentinelShield to test systems that you do not own or do not have permission to assess.

10. Database and Alert Persistence

MySQL provides persistent storage for SentinelShield. This is important because application memory is temporary.

Security Event ↓ Flask ↓ MySQL alerts table ↓ SOC Dashboard

Alerts remain stored after the Flask application restarts, provided that the database is maintained correctly. Regular database backups should be maintained for important data.

11. ngrok Testing

During development, ngrok can temporarily expose the local Flask application for authorized testing. 

ngrok http 5000

When a reverse proxy such as ngrok is used, request.remote_addr may show a proxy or local address instead of the original client address. Trusted forwarded headers can be processed when the proxy configuration is properly controlled.

In production, do not blindly trust client-supplied forwarded headers. Only trust headers from a correctly configured trusted proxy.

12. Security Limitations

SentinelShield uses rule-based detection. It is a learning and demonstration project and is not a replacement for a full enterprise IDS/IPS or commercial SOC platform.

  • False positives
  • False negatives
  • Encoded or obfuscated attack inputs
  • New attack techniques not covered by rules
  • Proxy/IP attribution issues
  • In-memory brute-force counters may reset after restart

Recommended production controls

  • Proper authentication and authorization
  • Password hashing
  • Rate limiting
  • Secure session management
  • Input validation
  • Output encoding
  • CSRF protection
  • Secure HTTP headers
  • Centralized logging
  • Log rotation
  • Database backups
  • Secure API-key and secret management
  • Trusted reverse-proxy configuration
